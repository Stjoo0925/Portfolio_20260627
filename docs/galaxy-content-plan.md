## 1. 은하 표현 고도화

### 1.1 설계 원칙

1. **드로우콜을 늘리지 않는다.** 별은 지금처럼 단일 `<points>` 하나. 다양성은 전부 per-vertex attribute와 셰이더로 만든다.
2. **가산 블렌딩의 한계를 인정한다.** additive에서는 "어두운 먼지 띠"를 그릴 수 없으므로, 먼지는 *별을 빼는 방식*(밀도 마스크)으로 표현한다.
3. `perfLevel === "low"` 경로를 항상 함께 설계한다. 신규 레이어는 low에서 전부 스킵.

### 1.2 단계별 작업

#### Phase A — 구조: 3-레이어 은하 (가장 큰 체감, 리스크 낮음)

기존 2분기(원반/헤일로)를 4분기로 교체:

| 레이어 | 비율 | 분포 |
|---|---|---|
| **핵 (bulge)** | 12% | 구형, `r = pow(rand, 2.2) * 5.5`, y 축소 0.7배 → 밀집 발광 코어 |
| **나선팔** | 52% | 로그 나선 (아래) + 가우시안 팔 폭 |
| **원반 배경** | 22% | 팔에 속하지 않는 원반 별, y 산포 넓게 → 팔이 "빈 곳에서 튀어나온" 것처럼 안 보이게 |
| **헤일로** | 14% | 현재 구형 헤일로 유지, 반경 확대 |

로그 나선 (핵심 수식):

```
const PITCH = 0.42;            // 감김 정도 (실제 은하 pitch angle 12~15°)
const r = 4 + Math.pow(random(), 0.7) * 38;
const arm = (random() > 0.5 ? 0 : Math.PI);
// 가우시안 팔 폭: 안쪽은 좁고 바깥은 넓게 (실제 은하의 팔 확산)
const spread = gauss(random) * (0.10 + r * 0.006);
const angle = arm + Math.log(r / 4) / PITCH + spread;
```

`gauss()`는 `(rand+rand+rand-1.5)` 3항 합 근사 — 이미 `:242`에서 y 산포에 쓰던 패턴을 재사용.

원반 두께는 반경에 따라 얇아지게(`flare` 역방향): `y = gauss * (1.4 - r*0.02)` → 중심부가 두껍고 외곽이 얇은 렌즈형 실루엣.

#### Phase B — 색: 색온도 구배 (두 번째로 큰 체감)

`aColor` attribute(vec3) 추가, `uColor`는 *곱해지는 전역 틴트*로 역할 변경. 라우트 accent 틴트 로직(`:380-392`)은 그대로 살아있고 별의 고유색 위에 얹힌다.

```
핵      → #FFD9A8 ~ #FFC170  (늙은 K/M형, 황금)
팔      → #BFD8FF ~ #FFFFFF  (젊은 O/B형, 청백) + 3% 확률로 #FF9E7A (HII 영역)
원반    → #E8EAF0            (중간 톤)
헤일로  → #C9CEDA            (창백, 채도 낮게)
```

메모리 절약: `Uint8Array` + `normalized: true`로 넘김 (2800개 × 3바이트).

#### Phase C — 밝기/크기 분포 + 회절 스파이크

- 크기를 멱법칙으로: `size = 0.28 + Math.pow(random(), 3.4) * 3.2` → 대부분 미세, 소수만 크게. 밝은 별이 bloom(`galaxy-canvas.tsx:28`, threshold 0.35)을 실제로 트리거해서 "사진 같은" 질감이 생긴다.
- 상위 ~1.5% 밝은 별에만 **4방향 회절 스파이크**: 프래그먼트에서 `gl_PointCoord` 기반 십자 게이트를 `aSpike` 세기로 곱해 추가. 별도 레이어·별도 텍스처 불필요.

```glsl
// FRAGMENT에 추가
vec2 q = abs(gl_PointCoord - 0.5);
float cross_ = max(
  smoothstep(0.5, 0.0, q.x * 14.0) * smoothstep(0.5, 0.0, q.y),
  smoothstep(0.5, 0.0, q.y * 14.0) * smoothstep(0.5, 0.0, q.x)
);
a += cross_ * vSpike * 0.5;
```

#### Phase D — 차등 회전 (은하가 "살아 있게")

강체 회전(`:414`)을 셰이더 내 반경 의존 회전으로 교체. 실제 은하는 안쪽이 빠르게 도므로, 안쪽이 앞서 감기는 시어(shear)가 생겨야 한다.

```glsl
uniform float uSpin;   // 누적 각도 (JS에서 delta 적산 — 시간 점프 방지)
float rad = length(position.xz - vec2(0.0, -10.0));
float w = 1.0 / (rad * 0.10 + 1.0);      // 안쪽 빠름
float ang = uSpin * w;
// position을 원반 중심 기준으로 회전
```

주의: 무한히 돌리면 팔이 완전히 감겨 사라진다. 대신 **시어 폭을 ±0.35rad로 클램프**하고 그 안에서 아주 느리게 왕복 — "숨 쉬는 팔"이 되고 형태는 영구히 유지된다. 그룹 회전(`groupRef`)은 전체 세차운동용으로 훨씬 느리게(0.0012) 남겨둔다.

#### Phase E — 기울기 + 성간물질 (분위기 레이어, high only)

1. **원반 경사 20°**: `<group rotation={[0.35, 0, 0.08]}>`로 감싸 원반을 타원으로 보이게. 노드는 이 그룹 밖에 있으므로 인터랙션 좌표계에 영향 없음 (단, `:405-407`의 lens 역회전 보정에 tilt를 함께 반영해야 함 — **이 부분이 유일한 회귀 위험 지점**).
2. **먼지 띠**: 팔 내부 반경 0.75 지점에 밀도 마스크 — 해당 각도 밴드에 있는 별을 생성 단계에서 15% 확률로 드롭. 별이 없는 곳이 곧 먼지 띠로 읽힌다.
3. **성운 3~4장**: 팔 위에 큰 소프트 빌보드(반경 4~7, alpha 0.05, additive, 청록/자홍). `<Billboard>` 없이 `sprite` 3~4개 = 드로우콜 +4. 원반 그룹 안에 넣어 함께 회전.
4. **코어 글로우**: 중심에 반경 8 소프트 스프라이트 1장(황금, alpha 0.12). 이거 한 장이 "은하 핵"의 인상을 절반 이상 만든다.

#### Phase F — 오프닝 시퀀스 정합

현 `formPos`는 Y축 기준 공통 소용돌이(`:45`)를 이미 쓰고 있어 방향성은 맞습니다. Phase D 도입 후에는 **infall 소용돌이 방향 = 차등 회전 방향**이 되도록 부호를 맞춰야 하고, `uSpin`은 `form < 1` 구간에서 0으로 잠가야 이중 회전이 안 걸립니다.

### 1.3 성능 예산

| | low | high |
|---|---|---|
| 별 | 1200 → 1600 (attribute만 추가, 부담 미미) | 2800 → 4200 |
| streak | 180 (유지) | 560 (유지) |
| 성운/코어 스프라이트 | 코어 1장만 | 4~5장 |
| 차등 회전 | 적용 (셰이더 연산, 사실상 무료) | 적용 |
| 회절 스파이크 | 미적용 | 적용 |

프레임 코스트는 거의 전부 fragment fill(가산 블렌딩 오버드로)입니다. `gl_PointSize` 상한 46(`:87`)은 유지하고, 성운 스프라이트 alpha를 0.05 이하로 묶는 것이 60fps 유지의 핵심입니다.

### 1.4 검증 방법

메모리에 기록된 대로 브라우저 패널이 숨겨지면 WebGL이 멈추므로, **headless Playwright 스크린샷**으로 검증합니다 (`galaxy-check*.tmp.mjs` 패턴 재사용). 체크 항목:

- `/` 진입 3초 후 정지 프레임 — 나선팔 2개가 로그 나선으로 감겨 보이는가
- 핵의 황금 톤과 팔의 청백 톤이 육안으로 구분되는가
- 노드 호버 시 gravity lens가 여전히 정확한 노드 위치에 걸리는가 (tilt 회귀 확인)
- 10초 구간 프레임 타임 (dev overlay 또는 `requestAnimationFrame` 샘플링)

#### Skills — 나열에서 맥락으로

```json
{
  "categories": [
    {
      "name": "Frontend",
      "items": [
        { "name": "React", "level": "core", "context": "Narrativa, Afterburner, 본 포트폴리오" },
        { "name": "TypeScript", "level": "core", "context": "전 프로젝트 기본" },
```

`level`은 3단계만 (`core` / `working` / `familiar`). 퍼센트 막대는 쓰지 않습니다 — 근거 없는 "React 85%"는 오히려 신뢰를 깎습니다. 대신 **"어디서 썼는지"**를 붙이면 그 자체가 증거가 됩니다. 시각적으로는 core 항목만 밝은 실버, working/familiar는 톤 다운한 칩으로 위계를 만듭니다.

빠진 스택 보강: Next.js, Supabase, Vue/Pinia, Jenkins, Vercel, Netlify, Firebase — 프로젝트 태그에는 있는데 skills에 없습니다.

- `links`가 전부 빈 문자열 → GitHub 링크만이라도 채우고, 없으면 카드에 링크 자리 자체를 렌더하지 않기 (빈 아이콘은 미완성으로 읽힘).
- 회고 패널에 **"문제 → 접근 → 결과"** 순서를 명시적 소제목으로. 지금 `overview/learnings/challenges/nextSteps`는 좋은 데이터인데 순서가 서사가 아닙니다.
- `nextSteps`에 "데모 링크 보강 예정" 같은 **미완성 고백은 삭제**. 회고는 배우려는 태도의 증거지만, 산출물 부재를 명시하는 문장은 감점입니다.

#### Lab — 형태 다양성을 전면에

please_readme(Web) / Gitagotchi(VS Code Extension) / MarkUI(Desktop) / Renam — **하나의 문제를 웹·IDE·데스크톱 세 가지 형태로 풀어봤다**는 게 강한 신호인데 지금은 카드 목록에 묻혀 있습니다.

- 섹션 인트로 아래 형태별 필터/그룹: `Web` `IDE Extension` `Desktop`
- Marketplace 배포된 Gitagotchi에는 `v1.0.0 · Marketplace 배포` 배지 — "만들어봤다"와 "출시했다"는 다릅니다.
- Gitagotchi 회고의 i18n(한/영/일/중) 언급은 Skills의 근거로도 재사용.

### 2.4 3D 은하와 콘텐츠의 연결 (지금 놓치고 있는 것)

노드 6개가 라우트 6개에 1:1로 매핑돼 있고 `galaxyConnections`(`lib/galaxy/nodes.ts:37-46`)로 연결선까지 정의돼 있는데, **그 연결이 콘텐츠적으로 의미가 없습니다** (`connection-lines.tsx`는 삭제된 상태). 은하 그래프를 서사로 쓸 기회:

- `experience → projects` = "현장 경험이 프로젝트로"
- `projects → lab` = "팀 작업이 개인 실험으로"
- `about → contact` = 시작과 끝

각 연결에 짧은 라벨을 주고, 호버 시 그 문구를 노출하면 은하 자체가 **인터랙티브 목차**가 됩니다. 이게 "예쁜 3D 배경"과 "이 사람만의 포트폴리오"를 가르는 지점입니다.

또한 노드 `radius`가 `projects`만 1.05로 크고 나머지는 0.72~0.86입니다 — 콘텐츠 분량/중요도와 반지름을 정렬해서 은하가 곧 정보 위계가 되게 합니다.

### 2.5 배포 전 필수 정리

- `content/site.json`의 `url`: `http://localhost:3000` → 실제 도메인 (OG/canonical에 직결)
- `links.linkedin` 빈 값 처리 또는 제거
- `projects.json`의 모든 `links` 채우기 또는 조건부 렌더
- `contact.json`의 `closing`이 빈 문자열 → 채우거나 스키마에서 optional 처리
- `projects.json` Afterburner 회고의 "다 플랫폼(웹+앱)" → "다중 플랫폼"
- `content/site.json`의 `initials`가 `JS`인데 이름은 SoonTae Joo → `SJ` 또는 `ST`로 정합성 확인
